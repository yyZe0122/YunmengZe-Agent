# Execution boundaries

`agent` mode executes tools with the current OS account's filesystem, process and network access. Paths may be absolute and outside the launch directory. Shell commands and MCP servers run with that access; the application has no approval prompts, capability grants or workspace allowlist. Use an externally managed account or sandbox when OS isolation is required.

`plan` is enforced by [tools.Registry.Execute](internal/tools/registry.go) as well as the tool list sent to the model. It blocks file writes, shell, preference changes and MCP. Child sessions inherit plan, explore children always use plan, and every child is a leaf. Plan still saves conversations and summaries and may initialize or migrate the database. When memory is enabled, initialization may archive expired legacy non-preference records; preference expiry is filtered by `expires_at` without creating a forget marker. Plan does not curate preferences, but can contact providers and enabled web or image services.

Disabled capabilities are omitted from the tool registry. These [configuration switches](docs/wiki/configuration.md) control application features: disabling web also blocks web child tasks, but does not restrict OS networking, MCP traffic or image URLs. Disabling memory preserves its stored records and migration history. Explicit forget and existing archives continue to block automatic recovery of the same preference key; naturally expired preferences may be learned again from fresh evidence.

Each tool call receives cancellation and a deadline. The [tool reference](docs/wiki/tools.md) documents output and input limits; shell cancellation terminates the process tree, and cancellation of an active MCP stdio call closes its pipes, terminates its process tree and waits for it to exit. File write/edit hash preconditions detect content changes between reading and editing, but do not provide a transaction across operations or a rollback system.

Rules, skills and memory are instruction text. Injection scanning and linked-file containment apply at their respective loading paths; they do not grant tools or guarantee protection against prompt injection. Skill bodies and linked files have a 1 MiB read limit. Suspicious phrases produce diagnostics; invalid encoding and hidden control characters still fail validation. Phrase scanning is not a security boundary. Remote pages and MCP responses are external task data.

Conversation messages and memory are stored in `core.db`. Provider requests include the context assembled by the engine; image tools send their inputs to the configured services. TUI diagnostics are appended to the configuration directory's `ymz.log`. Treat the configuration directory, conversation database and diagnostic output as private.

Keep keys in environment variables, the configuration directory's `env`, or referenced files. Do not commit secrets or runtime data. Configuration and credential resolution results, including failures for unused models, are fixed at startup; restart after changing them. `ymz config validate` checks the main model and enabled-feature dependencies, reports other unavailable models without printing resolved credentials, and does not validate remote authentication. Review tool errors and logs before sharing them because external services can include their own diagnostic text.

To report a vulnerability, use GitHub's private vulnerability reporting for this repository when available. Include the affected version, OS, reproduction steps and expected boundary, with credentials and private conversation data removed.
